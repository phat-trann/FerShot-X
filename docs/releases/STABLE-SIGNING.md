## Configured personal certificate without Developer ID

A persistent self-signed Code Signing certificate can provide a stable designated requirement for personal use. It does not provide Apple notarization or public Gatekeeper trust; privacy behavior must still be tested on the actual macOS installation. Apple documents self-signed identity creation in [Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html). An Apple-issued identity remains an alternative if policy changes later.

1. In Keychain Access, use Certificate Assistant > Create a Certificate. Choose a unique persistent name, Self Signed Root and Code Signing. Create once, with an appropriate validity period, and securely back up the certificate/private key. Do not regenerate it for each release. Any local trust approval is a deliberate user action; do not disable Gatekeeper or change global privacy databases.
2. Export this identity and its private key as a .p12; an empty export password is supported. Keep it private. Convert it locally to base64 using the standard Tauri instructions; do not send certificate/private-key/password contents in chat or put them in Git.
3. In GitHub environment `release`, set variable `MACOS_SIGNING_IDENTITY` to the exact signing identity name. Set secret `APPLE_CERTIFICATE` (base64 .p12). `APPLE_CERTIFICATE_PASSWORD` is optional: omit it for the user's passwordless certificate. These are app-signing credentials, separate from the existing `TAURI_SIGNING_PRIVATE_KEY` pair, which must remain unchanged.
4. CI requires the certificate/identity, imports them into a new temporary runner keychain and proves signing before building. There is no ad-hoc release fallback. The final universal app and downloaded updater archive must verify with the exact imported certificate on both architectures before publishing. Existing keychain entries/trust stores remain untouched; the temporary keychain and runner search-list changes are cleaned up even on failure. The current identity is FerShot X, as configured by the user. First real CI signing is still distinct from injected tests.
5. On the first move from ad-hoc to the persistent identity, macOS may ask for Screen Recording, Accessibility and Keychain approval once more. Verify the signer and app path, then approve the intended app. For Keychain, use Always Allow only if offered for this app and you trust the installed build. Do not change the item to allow all applications.
6. Publish another version using the exact same identity, update in-app, and verify Capture, Scroll Capture and FTP/HTTP Keychain access without another identity-change prompt. Some periodic OS prompts may still be required by macOS. Record the two versions, OS and the observed prompts before closing checklist item 16.

No certificate/private key was generated or read by the agent. No real OS permissions, trust stores or Keychain ACLs were modified. CI certificate/signing and signed-to-signed continuity remain manual/external acceptance. [Official Tauri signing configuration](https://v2.tauri.app/distribute/sign/macos/).
